# ADR-001 — Scripture Reading Session Marker Detection

## Status

Accepted for CP-014 Review

## Date

24 July 2026

## Decision Type

Domain and Data Recognition Rule

---

## 1. Context

Live Streamlit testing during CP-014 exposed an inconsistency in the current session-detection assumption.

The existing implementation and/or previous working assumption treated the exact phrase:

SCRIPTURE READING

as the primary session marker.

However, the real WhatsApp export demonstrates that the Scripture Reading announcement may use different wording.

Example:

*FIRST SCRIPTURE ON FOR THE YEAR 2023...SUNDAY 1ST OF JANUARY 2023*

followed by:

*GENESIS 1-2*

*MATTHEW 1*

The actual message therefore does not necessarily need to contain the exact phrase:

SCRIPTURE READING

The system must recognize the actual structure of the group's Scripture Reading activity rather than depend on one exact phrase.

---

## 2. Decision

A Daily Session shall be identified by the posting of a valid Scripture Reading message.

The session marker shall not depend exclusively on the exact phrase:

SCRIPTURE READING

A valid Scripture Reading marker is identified by the presence of:

1. A day of the week.
2. A written calendar date.
3. A written month.
4. A year.
5. A recognizable Bible reading reference.

The date written in the Scripture Reading message is the identity/date of the reading session.

The WhatsApp message timestamp is the actual posting time of the Scripture Reading activity.

These two dates must not be confused.

---

## 3. Critical Date Distinction

The following are separate concepts.

### 3.1 Message Timestamp

The timestamp generated by WhatsApp:

[1/1/2023, 1:03:34 PM]

This represents when the message was posted.

### 3.2 Scripture Reading Date

The date written inside the message:

SUNDAY 1ST OF JANUARY 2023

This represents the Bible reading day being announced.

The two dates may differ.

For example, a Scripture Reading message may be posted several hours before the actual reading date.

That does not invalidate the Scripture Reading marker.

The session begins at the point where the Scripture Reading message is posted.

Therefore:

Message Posted
        ↓
Scripture Reading Activity Detected
        ↓
Session Begins
        ↓
Reading Date Stored as Session Identity

The system must not reject a valid Scripture Reading message merely because the written reading date does not equal the WhatsApp message date.

---

## 4. Session Boundary Rule

A new Daily Session begins when a valid Scripture Reading message is posted.

The conceptual flow is:

Valid Scripture Reading Message
            ↓
       New Session
            ↓
All subsequent messages
belong to that session
until the next valid Scripture Reading message.

The session marker is therefore an activity event.

The system should treat the Scripture Reading message as:

ActivityType.SCRIPTURE_READING

and use that event to establish the beginning of the Daily Session.

## 6. Recognition Example

The following sequence qualifies as a Scripture Reading Session Marker:

*FIRST SCRIPTURE ON FOR THE YEAR 2023...SUNDAY 1ST OF JANUARY 2023*

*GENESIS 1-2*

*MATTHEW 1*

The system should recognize:

Reading Date:
Sunday, 1 January 2023

Bible Reading:
Genesis 1-2
Matthew 1

The WhatsApp timestamp of the message establishes when the Scripture Reading activity occurred.

The written date establishes the reading date associated with the session.

---

## 7. Message Date Must Not Be Used as a Rejection Rule

The following must not automatically invalidate a Scripture Reading marker:

WhatsApp Message Date != Written Reading Date

For example:

WhatsApp Message Date:
31 December 2022

Written Reading Date:
Sunday 1st of January 2023

This may be a perfectly valid Scripture Reading announcement.

The session should still begin when the Scripture Reading message is posted.

---

## 8. Expected Session Count

The study program is organized around approximately one Daily Session per day.

For a complete 365-day study year, the expected result is approximately:

365 Scripture Reading Activities
≈
365 Daily Sessions

This is an important domain validation expectation.

The system should therefore make it possible to investigate discrepancies such as:

Expected:
365 Scripture Reading Activities

Detected:
350 Scripture Reading Activities

or:

Expected:
365 Daily Sessions

Detected:
348 Daily Sessions

The difference should trigger investigation into:

- Missed markers.
- Unrecognized message variations.
- Duplicate markers.
- Missing export data.
- Date-range filtering.
- Invalid or incomplete source data.

---

## 9. Iterative Session Loading Concern

The application is designed to process sessions iteratively rather than attempting to load and analyze the entire export as one undifferentiated operation.

The intended conceptual flow is:

Filtered WhatsApp Messages
        ↓
Detect First Session Marker
        ↓
Build Session 1
        ↓
Analyze Session 1
        ↓
Detect Next Session Marker
        ↓
Build Session 2
        ↓
Analyze Session 2
        ↓
Continue Until End of Range

This approach is important because a WhatsApp export may contain a large number of messages.

The system should avoid unnecessary token, memory, and processing pressure by processing the data session by session where appropriate.

---

## 10. Timeline Selection Concern

The application must support selecting a specific analysis period.

The user should be able to define:

Start Date
+
End Date

The system should then analyze only the relevant portion of the WhatsApp export.

Conceptually:

Full WhatsApp Export
        ↓
Start Date
        ↓
End Date
        ↓
Filtered Message Range
        ↓
Session Detection
        ↓
Iterative Session Processing

The interaction between date-range selection and session detection requires particular care.

A Scripture Reading message may be posted before the written reading date.

Therefore, filtering solely by the written reading date or solely by the message timestamp may produce different results.

The implementation must define and preserve the correct boundary semantics.

---

## 11. Boundary Semantics to Preserve

The following principle is required:

The Scripture Reading activity occurs when the Scripture Reading message is posted.

Therefore:

Message Timestamp
        ↓
Activity Event Timestamp
        ↓
Session Start Boundary

The written date inside the message is session metadata and should not replace the message timestamp as the activity occurrence time.

---

## 12. Consequences

### Positive Consequences

- The system becomes more tolerant of real-world WhatsApp message variation.
- Session detection is based on the actual business activity.
- The exact phrase SCRIPTURE READING is no longer a single point of failure.
- The system can distinguish message posting time from reading identity/date.
- Expected annual session counts can be used for validation.
- Iterative session processing remains compatible with large exports.
- User-selected timelines can be supported without losing the session boundary model.

### Risks

- Bible reference recognition must be sufficiently robust.
- The system must avoid false positives from ordinary messages containing dates and Bible references.
- Date-range filtering must be carefully defined.
- A session marker may span multiple contiguous messages rather than a single message.
- The parser must support the actual variations used in the WhatsApp group.

---

## 13. Implementation Status

This ADR records the business and architectural decision.

The existing implementation must be reviewed against this decision during:

CP-014 — Presentation Layer Completion & Integration Review

The session-detection implementation must not be modified until the current detection flow has been inspected and the required changes have been identified.

---

## 14. Final Rule

A Daily Session begins when a valid Scripture Reading message is posted.

A valid Scripture Reading marker is identified through the group's recognizable Scripture Reading structure, including a day of the week, written calendar date, month, year, and recognizable Bible reading reference.

The written reading date identifies the reading associated with the session, while the WhatsApp message timestamp identifies when the Scripture Reading activity occurred and establishes the session boundary.

The two dates are not required to be identical.
