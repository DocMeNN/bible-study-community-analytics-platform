# CP-017.3 — Multi-Session Analytics Contract Design

## Online Bible Study Attendance and Participation Analytics Platform

**Repository:** `bible-study-community-analytics-platform`
**Checkpoint:** `CP-017.3`
**Parent Phase:** `CP-017 — Multi-Session Analytics Integration`
**Status:** **APPROVED**
**Next Step:** Application Service Integration

---

# 1. PURPOSE

This document defines the application-level contract required to integrate the selected multi-session Presentation scope with the analytics layer.

The objective is to transition the platform from:

```text
Selected Daily Session
        ↓
Application Service
        ↓
Single-Session Analytics
```

to:

```text
Selected Presentation Scope
        ↓
SessionGroup
        ↓
Multiple Daily Sessions
        ↓
Application Service
        ↓
Multi-Session Analytics
```

The architecture must preserve the established domain principle:

> **Daily Session remains the atomic Domain and storage unit.**

The system will not replace the `Daily Session` Domain model with a new multi-session Domain aggregate merely to support presentation-level grouping.

---

# 2. CURRENT ARCHITECTURE

The current analytics flow is:

```text
SessionCollection
        ↓
context.current_session()
        ↓
Single Daily Session
        ↓
ViewModel
        ↓
Application Service
        ↓
Domain Analytics
```

The current Presentation layer extracts a single `Session` before the analytics workflow begins.

The current conceptual flow is therefore:

```text
┌──────────────────────────┐
│    SessionCollection     │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│   Current Daily Session  │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│       ViewModel          │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│   Application Service    │
└────────────┬─────────────┘
             ↓
┌──────────────────────────┐
│     Domain Analytics     │
└──────────────────────────┘
```

This architecture is valid for Daily presentation.

However, it does not yet support:

```text
Weekly
Monthly
First Half
Second Half
Yearly
```

analytics across multiple Daily Sessions.

---

# 3. PROBLEM STATEMENT

The Presentation layer now supports grouping multiple Daily Sessions into a `SessionGroup`.

However, the analytics layer still operates primarily on a single:

```python
Session
```

The result is an architectural gap:

```text
Presentation Layer
        ↓
Multiple Daily Sessions
        ↓
Application Layer
        ↓
Single Session Contract
```

The Presentation layer can select a multi-session scope, but the Application layer does not yet have a formal contract for receiving that scope.

The missing boundary is:

```text
SessionGroup
        ↓
?????????????
        ↓
Application Analytics
```

CP-017.3 defines this missing contract.

---

# 4. ARCHITECTURAL DECISION

The Application layer shall receive a multi-session analytical scope through an application-level abstraction.

The target architecture is:

```text
SessionCollection
        ↓
Presentation Grouping
        ↓
SessionGroup
        ↓
Analytical Scope
        ↓
Application Services
        ↓
Domain Analytics
```

The conceptual model is:

```text
┌─────────────────────────────┐
│      SessionCollection      │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│      SessionGroup           │
│                             │
│   Daily Session 1           │
│   Daily Session 2           │
│   Daily Session 3           │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│      Analytical Scope       │
│                             │
│   sessions                  │
│   scope boundaries           │
│   presentation period       │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│      Application Layer      │
└─────────────────────────────┘
```

# 5. SEPARATION OF RESPONSIBILITIES

The following responsibilities are explicitly separated.

## 5.1 Presentation Layer

The Presentation layer determines:

```text
Which period is selected
        ↓
Which SessionGroup is selected
        ↓
Which Daily Sessions belong to the current scope
```

The Presentation layer is responsible for:

* User selection
* Grouping configuration
* Session group navigation
* Current presentation scope
* Display state

The Presentation layer must not perform:

* Attendance aggregation
* Participant calculations
* Activity calculations
* Business rule evaluation
* Cross-session analytics calculations

---

## 5.2 Application Layer

The Application layer is responsible for:

```text
Selected Analytical Scope
        ↓
Application Workflow
        ↓
Domain Analytics
        ↓
Result DTO
```

The Application layer shall:

* Accept the selected multi-session analytical scope
* Orchestrate the participating Daily Sessions
* Invoke Domain analytics
* Aggregate results where aggregation is an application concern
* Return application results to ViewModels

The Application layer must not:

* Depend on Streamlit
* Depend on UI widgets
* Manage presentation rendering
* Own browser or session-state concerns

---

## 5.3 Domain Layer

The Domain layer remains responsible for:

* Daily Session business meaning
* Attendance rules
* Activity rules
* Done-event rules
* Scripture-reading rules
* Session-level analytics calculations
* Domain invariants

The Domain remains centred on:

```text
Daily Session
```

The Domain model is not replaced by:

```text
Weekly Session
Monthly Session
Yearly Session
```

These are presentation or analytical scopes, not replacements for the atomic Domain unit.

---

# 6. ANALYTICAL SCOPE

The multi-session analytics contract requires a conceptual analytical scope.

The scope represents the Daily Sessions selected for analysis.

Conceptually:

```text
AnalyticalScope
├── sessions
├── start_date
├── end_date
└── presentation_period
```

The scope represents:

```text
Selected Presentation Scope
        ↓
Daily Session 1
Daily Session 2
Daily Session 3
...
Daily Session N
```

The important distinction is:

```text
SessionGroup
        =
Presentation grouping
```

while:

```text
Analytical Scope
        =
Application analytics input
```

The Application layer should receive the sessions required for analysis without becoming dependent on Presentation-specific implementation details.

---

# 7. SERVICE CONTRACT EVOLUTION

The current Application Services are fundamentally session-oriented.

The current conceptual contract is:

```text
Session
    ↓
Application Service
    ↓
Result
```

CP-017 will extend this to:

```text
Analytical Scope
        ↓
Application Service
        ↓
Multi-Session Result
```

The existing single-session capability should not be removed unnecessarily.

The intended evolution is:

```text
Existing Single-Session Contract
                +
New Multi-Session Contract
```

This avoids unnecessarily breaking existing workflows and preserves Daily presentation compatibility.

---

# 8. ATTENDANCE ANALYTICS CONTRACT

Current conceptual flow:

```text
Session
    ↓
AttendanceService
    ↓
AttendanceResult
```

Target multi-session flow:

```text
Analytical Scope
        ↓
AttendanceService
        ↓
Multi-Session Attendance Result
```

The service must be capable of analysing the selected collection of Daily Sessions.

The result should distinguish between:

```text
Session-Level Attendance
```

and:

```text
Scope-Level Attendance
```

For example:

```text
Daily Session 1
    Participants: 42

Daily Session 2
    Participants: 48

Daily Session 3
    Participants: 39
```

The scope-level result may contain:

```text
Total Sessions
Total Attendance Events
Unique Participants
Average Attendance Per Session
```

The exact aggregation semantics must be implemented according to the existing domain rules and validated during CP-017.4.

---

# 9. ACTIVITY ANALYTICS CONTRACT

Current conceptual flow:

```text
Session
    ↓
ActivityService
    ↓
ActivityResult
```

Target:

```text
Analytical Scope
        ↓
ActivityService
        ↓
Multi-Session Activity Result
```

The service must support activity analysis across all Daily Sessions in the selected scope.

The analytical scope may contain:

```text
Session 1
    Activity Events: 98

Session 2
    Activity Events: 112

Session 3
    Activity Events: 87
```

The resulting scope-level analytics may include:

```text
Total Activity Events
Average Activity Events Per Session
Activity Distribution
Activity Trends
Participant Activity
```

The Application layer must orchestrate the scope.

The Domain layer remains responsible for the meaning of an activity event.

---

# 10. DASHBOARD ANALYTICS CONTRACT

The Dashboard Service is an orchestration service.

The current conceptual flow is:

```text
Session
        ↓
AttendanceService
        ↓
ActivityService
        ↓
DashboardResult
```

The target flow is:

```text
Analytical Scope
        ↓
AttendanceService
        ↓
ActivityService
        ↓
Additional Domain Analytics
        ↓
DashboardResult
```

The dashboard must represent the selected analytical scope.

For example:

```text
Weekly Scope
        ↓
7 Daily Sessions
        ↓
Weekly Dashboard
```

```text
Monthly Scope
        ↓
All Daily Sessions in Month
        ↓
Monthly Dashboard
```

```text
Yearly Scope
        ↓
All Daily Sessions in Year
        ↓
Yearly Dashboard
```

The dashboard must not silently continue using only:

```text
context.current_session()
```

when a multi-session scope is selected.

---

# 11. REPORT ANALYTICS CONTRACT

The Report Service coordinates the analytics services.

The current conceptual flow is:

```text
Single Session
        ↓
AttendanceService
ActivityService
DashboardService
        ↓
Report
```

The target flow is:

```text
Analytical Scope
        ↓
AttendanceService
ActivityService
DashboardService
        ↓
Multi-Session Report
```

The Report Service must therefore be capable of producing reports for the selected analytical scope.

The resulting report must accurately reflect:

```text
Selected Scope
        ↓
Sessions Included
        ↓
Analytics Population
        ↓
Report Results
```

The report must not combine:

```text
Selected Monthly Scope
```

with:

```text
Only the Current Daily Session
```

# 12. SESSION-LEVEL AND SCOPE-LEVEL ANALYTICS

CP-017 must distinguish between two analytical levels.

## 12.1 Session-Level Analytics

These operate on one Daily Session:

```text
Daily Session
        ↓
Session-Level Analytics
```

Examples include:

* Participants in one session
* Activities in one session
* Done events in one session
* Session-specific metrics

---

## 12.2 Scope-Level Analytics

These operate across the selected Daily Sessions:

```text
Session 1
Session 2
Session 3
        ↓
Scope-Level Analytics
```

Examples include:

```text
Total Sessions
Unique Participants
Total Events
Average Per Session
Participation Trends
Period Comparisons
```

The two levels must not be confused.

---

# 13. AGGREGATION PRINCIPLE

The following calculation must not be assumed to represent unique participants:

```text
Participants(Session 1)
+
Participants(Session 2)
+
Participants(Session 3)
```

For example:

```text
42 + 48 + 39 = 129
```

does not necessarily mean:

```text
129 Unique Participants
```

The same participant may appear in multiple sessions.

Therefore:

```text
Total Attendance Events
```

and:

```text
Unique Participants Across Scope
```

are different metrics.

The analytics contract must preserve this distinction.

---

# 14. PROPOSED ANALYTICAL OUTPUT MODEL

The multi-session analytics results should conceptually support:

```text
Scope Analytics Result
├── scope metadata
├── sessions included
├── session-level results
└── aggregated scope-level results
```

Conceptually:

```text
Scope
│
├── Session 1
│   └── Session Analytics
│
├── Session 2
│   └── Session Analytics
│
├── Session 3
│   └── Session Analytics
│
└── Scope Summary
```

This allows the platform to support both:

```text
Detailed Session-Level Analysis
```

and:

```text
Aggregated Scope-Level Analysis
```

without destroying the Daily Session atomic model.

---

# 15. COMPATIBILITY REQUIREMENT

The implementation must preserve the existing Daily presentation.

When the selected Presentation scope contains exactly one Daily Session:

```text
SessionGroup
        ↓
1 Daily Session
```

the system should remain capable of producing the existing single-session analytical experience.

Therefore:

```text
Daily Presentation
        ↓
One Daily Session
        ↓
Analytics
```

must remain valid.

The new multi-session capability must extend the existing architecture rather than unnecessarily replace it.

# 17. ARCHITECTURAL RULES

The following rules are mandatory for CP-017 implementation.

### Rule 1

`Daily Session` remains the atomic Domain and storage unit.

### Rule 2

`SessionGroup` is a Presentation grouping concept.

### Rule 3

The Presentation layer selects the analytical population.

### Rule 4

The Application layer orchestrates the selected Daily Sessions.

### Rule 5

The Domain layer performs Domain calculations and enforces business rules.

### Rule 6

The Presentation layer must not perform cross-session aggregation calculations.

### Rule 7

The Application layer must not depend on Streamlit implementation details.

### Rule 8

The existing Daily/single-session workflow must remain functional.

### Rule 9

Scope-level metrics must be distinguished from session-level metrics.

### Rule 10

Multi-session analytics must not silently fall back to `current_session()` when a multi-session scope is selected.
